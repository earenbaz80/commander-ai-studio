**Por qué.** `src/agent/permissionRules.ts` evalúa reglas `allow`/`ask`/`deny` en `localStorage`; el servidor no las conoce, así que el CLI puede ejecutar algo que el escritorio bloquearía. La paridad de permisos es criterio explícito de F1.

**Alcance**
- Persistir las reglas también en `.commander/permissions.json` (`rules[]`), manteniendo la UI como editor y una migración única desde `localStorage`.
- Evaluar `decide()` en el servidor antes de aprobar o ejecutar; `deny` gana siempre, `allow` evita el prompt, `ask` fuerza aprobación.
- La regla `deny` no se puede saltar con `allow-session` ni con `--yes`.
- Exponer `GET/PUT /api/agent/permission-rules?root=` para que la UI y el CLI lean la misma fuente.

**Criterios de aceptación**
- [x] Una regla `deny` del escritorio bloquea la misma tool en el CLI.
- [x] Una regla `allow` evita el prompt en CLI y en escritorio.
- [x] `ask` fuerza prompt aunque la tool no sea `danger`.
- [x] Las reglas son por proyecto y no viajan con el repo si `.commander/` está ignorado.
- [x] 10 casos adversariales (shell, escritura, red, MCP, subagente) no ejecutan nada fuera de política.

**Implementación.** `permissions.ts` guarda `rules[]` y `rulesImportedAt` junto al modo, las listas y los globs, con escritura atómica (`tmp` + `rename`) y helpers `getPermissionRules`/`setPermissionRules`. `server.ts` añade `GET/PUT /api/agent/permission-rules?root=`; el PUT con `migrate` fusiona una sola vez las reglas de `localStorage` (`mergeRuleSets`) y marca `rulesImportedAt`, y el PUT de `/api/permissions` conserva las reglas para que el panel no las pise. La evaluación ocurre en dos puntos:

- `agentTools.executeAgentToolCore`: tras `enforceTool`, un `decide(...) === 'deny'` devuelve `403` antes de despachar la tool. Esto cubre al CLI headless (que llama `POST /api/agent/run-tool`) y a cualquier sesión.
- `agentSession.runOne`: antes de pedir aprobación, `deny` corta la llamada y `needsHumanApproval` decide el prompt: `ask` siempre pregunta, `allow` nunca y, sin regla, se mantiene la política anterior (peligro + allow-session). Así `allow-session` y `--yes` no pueden saltar un `deny`.

`ruleTarget` extiende el objetivo del patrón a `mcp.call`/`mcp.*` y `task` (el nombre de la tool), de modo que las reglas también cubren MCP y subagentes, no sólo shell y escritura. En el escritorio, `AgentApprovalModal` sincroniza al montar (`syncRulesWithServer`) y persiste cada regla nueva con `persistRuleToProject`, sin dejar de escribir en `localStorage`.
