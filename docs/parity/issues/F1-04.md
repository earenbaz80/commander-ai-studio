**Por qué.** Es el hueco de seguridad y de producto más grande: el CLI no puede aprobar nada, y el servidor ejecuta tools peligrosas con sólo el modo y la allowlist. Sin canal, `--write` y las tools que piden aprobación no son equivalentes al escritorio.

**Alcance**
- `ApprovalRequestV2`: `{id, sessionId, tool, input, diff?, hunks?, createdAt, expiresAt}`; `POST /api/agent/sessions/:id/approvals/:approvalId` con `{decision: 'allow'|'deny'|'allow-session', reason?}`.
- El bucle pide aprobación para toda tool marcada `danger`, `github.comment`, `shell.run` fuera de allowlist y toda escritura; las de lectura no preguntan.
- Timeout de 5 min → `deny` con motivo `timeout`; cancelar la sesión resuelve todas las pendientes como `deny`.
- Idempotencia: repetir la misma decisión devuelve 200 con el mismo resultado; una decisión distinta sobre una ya resuelta devuelve 409.
- `allow-session` recuerda la regla sólo para esa sesión, nunca en disco.

**Criterios de aceptación**
- [x] Denegar una escritura no modifica ni un byte (hash del árbol antes/después idéntico).
- [x] Aprobar aplica el cambio y el paso queda en el estado con su decisión.
- [x] `allow-session` no vuelve a preguntar la misma tool+patrón dentro de la sesión y no afecta a otra sesión.
- [x] Un timeout deniega y la corrida continúa sin ejecutar la tool.
- [x] Una decisión repetida es idempotente; una contradictoria responde 409.
- [x] Ningún approval incluye tokens ni rutas fuera del proyecto en el mensaje de error.

**Implementación.** `AgentSession` mantiene las pendientes y las decisiones
resueltas en memoria, emite `approval_request`/`approval_result` por el stream
v2 y expone `pendingApproval` en `SessionStateV2`. El endpoint HTTP traduce
200/400/404/409, el timeout y la cancelación en bloque viven en la sesión, y
`src/cli/agentClient.ts` exporta `respondApproval()` para que un cliente CLI
responda con la misma semántica. `allow-session` nunca se persiste.
