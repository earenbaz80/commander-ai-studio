> **Estado:** Implementado — `src/cli/diff.ts` y el prompt con `a`/`d`/`s`/`?`/`q` (2026-11-09). Cerrado como completado el 2026-11-09.

**Por qué.** Aprobar sin ver el cambio es peor que no aprobar. El escritorio ya muestra diff; el CLI necesita el mismo contenido, con contexto y sin dependencias nuevas.

**Alcance**
- Generador de diff unificado propio (contexto 3 líneas) para `fs.write` y `fs.edit`, reutilizando la lectura previa del archivo.
- Render por hunk con número de línea, `+`/`-`, color sólo si TTY y `NO_COLOR` ausente.
- Respuesta en el REPL: `a` aprobar, `d` denegar, `s` aprobar para la sesión, `?` detalle del hunk, `q` denegar y detener.
- Tope de 400 líneas mostradas con aviso de truncado explícito.

**Criterios de aceptación**
- [x] Un `fs.edit` de varias regiones muestra hunks separados y correctos.
- [x] `NO_COLOR=1` produce una salida estable, sin secuencias ANSI.
- [x] Un diff mayor que el tope lo dice y nunca finge estar completo.
- [x] Aprobar desde el diff aplica exactamente el contenido mostrado.

**Implementación.** `src/cli/diff.ts` parsea el diff unificado que calcula el servidor y lo pinta por hunk con números de línea, signos `+`/`-` y color sólo cuando la TUI lo tiene activo (TTY y sin `NO_COLOR`); `buildUnifiedDiff` comparte el motor de `src/utils/patch.ts`. El tope es `DIFF_MAX_LINES = 400`: al superarlo se cortan las líneas y se añade «… N línea(s) omitidas: diff truncado en 400, no está completo». El prompt de aprobación muestra el diff completo, acepta `a`/`d`/`s` además de las flechas y los números previos, `?` recorre los hunks con su detalle y `q` deniega y detiene la corrida reutilizando `onInterrupt`. En `agentSession`, el preview pasó de recortar el primer y último cambio a usar `diffLines`/`toUnifiedDiff`, así que una `fs.edit` con varias regiones llega como hunks separados.
